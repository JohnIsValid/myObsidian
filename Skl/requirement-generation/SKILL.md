# Skill：需求文档生成 - 编排层（Requirement Generation）

## 触发条件

当用户要求基于已确认的设计方案生成需求文档时使用本 Skill。
典型触发语句：「帮我生成需求文档」「把这个设计写成需求文档」「出文档」

## 角色定位

你是需求文档生成的编排调度器，负责：
1. 分析设计方案涉及的策划领域
2. 按领域调度对应的生成 Skill
3. 整合多领域产出，处理交叉引用
4. 加载 `doc-format-standard` Skill，确保最终文档符合格式规范

## 工作流程

### Step 1：接收并分析设计方案

收到用户的设计方案后：

1. **确认输入完整性**：检查设计方案是否包含以下必要信息，如有缺失则提示用户补充
   - 功能目标（为什么做）— **如果设计方案中没有策划自己表述的设计目的，应主动询问**：「请用 1-2 句话描述这个功能为什么要做、希望达到什么效果？」AI 基于策划的表述润色后写入文档的"设计目的"章节，不可自行编造设计目的
   - 核心流程（怎么运作）
   - 功能规则（具体怎么做）
   - 关联系统（影响什么）

2. **识别策划领域标签**：分析设计方案涉及哪些领域

   | 领域标签 | 判断依据 | 对应 Skill |
   |---------|---------|-----------| 
   | `#system` | 涉及功能逻辑、状态流转、数据模型、接口定义 | `req-system` |
   | `#gameplay` | 涉及大世界玩法、限时挑战、解谜、收集、对战等游戏循环 | `req-gameplay` |
   | `#leveldesign` | 涉及Boss战、副本规则、战斗遭遇、技能规格、场景布局、演出 | `req-leveldesign` |
   | `#numerical` | 涉及公式、概率、平衡性、成长曲线、资源产出 | `req-numerical`（待建设） |
   | `#narrative` | 涉及剧情、对话、文案内容、世界观 | `req-narrative`（待建设） |

3. **输出分析结果**：

```
## 设计方案分析

**功能名称**：[名称]
**涉及领域**：[#system] [#numerical] ...
**文档规模预估**：[小型/中型/大型]

### 生成计划
1. [领域1]：[该领域需要覆盖的内容概述]
2. [领域2]：[该领域需要覆盖的内容概述]
...
```

### Step 2：调度领域 Skill 生成

#### 单领域情况

当仅涉及一个领域时，直接读取对应领域 Skill 并按其指引生成文档。

- `#system` → 读取并遵循 `req-system` Skill
- `#gameplay` → 读取并遵循 `req-gameplay` Skill
- `#leveldesign` → 读取并遵循 `req-leveldesign` Skill

#### 多领域情况

当设计方案跨越多个领域时：

1. **拆分设计内容**：将设计方案按领域拆分为多个子块
2. **依次生成**：按领域逐一生成对应部分
3. **标记交叉引用点**：在生成过程中标记需要跨领域引用的位置

#### 配置表归属判断

在任何领域的文档生成进入"配置表"章节时，**必须**加载 `config-table-guide` Skill，按其归属判断流程决定每项配置应归入已有公共表还是新建独立表。禁止在未经归属判断的情况下直接为所有配置新建独立表。

#### 美术需求生成

在文档生成进入"美术资源"章节时，**必须**加载 `art-requirement` Skill，按其工作流从设计方案中提取美术需求并按项目实际需求表格式（动画/特效/原画）输出结构化条目。禁止使用自定义格式输出美术需求。

### Step 3：文档整合

当涉及多个领域时，将各领域产出整合为一份完整文档：

1. **统一文档结构**：按 `doc-format-standard` Skill 规范组织章节顺序
2. **合并功能概述**：将各领域的功能点合并到同一个功能概述章节
3. **处理交叉引用**：
   - 系统规则引用数值公式时，标注 `详见数值部分`
   - 系统状态触发文案时，标注 `文案内容详见文案部分`
   - 使用文档内链接格式辅助定位
4. **合并配置表需求**：各领域的配置需求合并到同一个配置规则章节
5. **合并美术资源**：各领域的美术资源需求合并到同一个美术资源章节

### Step 4：文档审查

生成完毕后，进行自检：

#### 格式合规检查

- [ ] 文档元信息是否完整（基本信息表 + 修改记录表）
- [ ] 前言章节是否完整（设计目的 + 如何达到 + 系统影响）
- [ ] 正文是否包含功能概述
- [ ] 每个功能模块是否有完整的规则描述
- [ ] 配置规则章节是否包含表结构定义
- [ ] 美术资源章节是否列出所有资源需求

#### 内容完整性检查

- [ ] 所有 UI 按钮是否列出了完整的状态（正常、置灰、高亮、已完成）
- [ ] 涉及列表/排行的功能是否说明了排序、刷新、重置、空状态规则
- [ ] 异常情况是否有处理方案
- [ ] 可配置的数值是否标注了 `可配置`
- [ ] 跨系统依赖是否标注了 `@负责人`

#### 术语一致性检查

- [ ] 文档中使用的术语是否与 `project-glossary.mdc` 一致
- [ ] 同一概念在全文中是否使用了统一的名称

### Step 5：输出并保存文档

#### 5.1 在对话中展示

将完整的需求文档输出给用户。如果文档较长，提供结构导航：

```
## 文档结构导航

- 前言
  - 设计目的
  - 如何达到设计目的
  - 功能对其他游戏系统的影响
- 正文
  - 功能概述
  - [模块1名称]
  - [模块2名称]
  - ...
- 配置规则
  - [表1名称]
  - [表2名称]
- 美术资源
```

#### 5.2 保存为本地文件（默认执行）

在对话中展示完文档后，**自动**执行以下保存操作：

1. **保存需求文档为 Markdown**：
   - 将完整文档内容写入 `.md` 文件
   - 默认路径：`~/user/lbworkspace/需求文档_<功能名称>.md`
   - 遵循 `design-conventions` §七 的文件输出约定

2. **导出美术需求 Excel**（如文档包含美术需求章节）：
   - 触发 `art-requirement` Skill 的 Step 4 导出流程
   - 默认路径：`~/user/lbworkspace/美术需求_<功能名称>.xlsx`

3. **告知用户保存结果**：
   - 列出所有已保存的文件及其完整路径
   - 提示用户工作区位置

## 领域 Skill 可用状态

| 领域 | 对应 Skill | 状态 |
|------|-----------|------|
| 系统策划 | `req-system` | **可用** |
| 玩法策划 | `req-gameplay` | **可用** |
| 关卡策划 | `req-leveldesign` | **可用** |
| 数值策划 | `req-numerical` | 待建设 |
| 文案策划 | `req-narrative` | 待建设 |
| 配置表归属 | `config-table-guide` | **可用** |
| 美术需求 | `art-requirement` | **可用** |

当用户的设计方案涉及尚未建设的领域 Skill 时：
- 告知用户该领域的专项 Skill 尚未建设
- 仍然基于 `doc-format-standard` Skill 的通用规范生成该领域的文档内容
- 在文档中标注 `[注：本部分使用通用规范生成，建议策划重点审查]`

## 注意事项

- 始终以 `doc-format-standard` Skill 为格式底线，任何领域 Skill 的产出都必须符合该规范
- 生成过程中加载 `design-conventions` Skill，确保设计惯例与约束被遵循
- 生成过程中引用 `project-glossary.mdc`（Rule，始终生效）确保术语一致性
- 当文档过长时（预计超过 500 行），建议用户按功能模块分文档
- 文档中不要生成占位的示意图 URL，界面描述段落后使用 `📌 【策划补图】` 格式标注（参照 `doc-format-standard` Skill §八 的规范）
- 每个界面描述段落完成后，**必须**紧接着插入图片占位标注，提示策划补充对应的界面示意图
- 文档生成完毕后，在美术资源章节之前插入**待补充界面示意图清单**，汇总所有需要策划补图的位置
- 配置表中的示例数据应尽量贴近实际场景，不要填充无意义的占位数据
- **设计目的**章节必须基于策划本人的表述润色生成，不可由 AI 自行编造；如策划未提供，应在 Step 1 主动询问
