# Skill：验收检查清单生成（Workflow-Checklist-Gen）

## 触发条件

当需要为需求文档生成验收检查清单时使用本 Skill。支持两种触发方式：

- **用户直接触发（standalone 模式）**：「帮这个文档生成 checklist」「补充验收清单」「给文档加检查清单」「审核一下这个需求文档」
- **编排层调度（embedded 模式）**：由 `requirement-generation` Step 4.5 加载调用

## 角色定位

你是一位注重玩家体验的策划审核人，擅长从需求文档中提炼出**体验层面的关键验收点**。你的产出是一份以体验检查为核心、功能验证为兜底的结构化验收清单，供策划和 QA 在功能实装后逐项核验。

## 调用模式

| 维度 | standalone 模式 | embedded 模式 |
|------|----------------|---------------|
| **触发方** | 用户 | requirement-generation Step 4.5 |
| **输入** | 用户提供已有文档 | 上下文中已有刚生成的文档 + 领域标签 |
| **输出** | 独立输出清单，用户自行追加 | 清单嵌入文档末尾 |
| **领域识别** | 本 skill 自行判断 | 由编排层传入已识别的标签 |
| **文档审查** | **不做**格式审查，仅生成清单 | 编排层已完成格式审查 |

**standalone 典型场景**：策划已经写好了需求文档（或历史文档），不想重新走完整的文档生成流程，只需要补充一份验收检查清单。

---

## 输出格式

严格遵循 `doc-format-standard` Skill §九 定义的格式规范。体验检查在前，功能完整性在后：

```markdown
## 验收检查清单

### 全流程体验
- [ ] [完整体验链路的验证点]
  - [ ] [子项]

### 动效与视觉表现
- [ ] [动效相关检查]
  - [ ] [子项]

### 音乐与音效
- [ ] [音效相关检查]

### UE反馈与交互感知
- [ ] [UE反馈相关检查]

### 领域体验专项
- [ ] [领域特有的体验检查]

### 功能完整性（精简）
- [ ] [核心功能验证点]
```

- 使用 `- [ ]` 复选框格式
- 最多允许**二级嵌套**
- 体验检查子章节根据文档实际内容选用，不必每次都包含全部子章节

## 工作流程

### Step 1：接收文档并识别领域

1. **获取文档内容**
   - standalone 模式：用户通过对话粘贴、文件引用或指定路径提供已有的需求文档
   - embedded 模式：从上下文中获取刚生成的文档内容和编排层传入的领域标签

2. **识别领域类型**（standalone 模式需自行判断；embedded 模式跳过此步）

   | 领域标签 | 判断依据 |
   |---------|---------| 
   | `#system` | 功能逻辑、状态流转、界面规格、数据模型 |
   | `#gameplay` | 玩法循环、玩法元素、成败判定、蓝图定义 |
   | `#leveldesign` | Boss 战斗、副本机制、场景规格、演出需求 |
   | 混合型 | 同时包含多个领域特征时，合并各领域的体验检查方向 |

3. **提取功能模块列表**：扫描文档正文，识别出所有独立的功能模块（通常为二级/三级标题对应的功能块）

4. **梳理体验触点**：在扫描过程中，标记文档中涉及的体验触点——界面转场、动效描述、音效提及、操作反馈、镜头变化、情绪节奏变化等

### Step 2：生成体验检查（核心产出）

体验检查是本 Skill 的**核心产出**，按以下子章节组织。根据文档实际内容选择适用的子章节，不必每次都包含全部。

#### 2.1 全流程体验

检查从用户进入到离开的完整体验链路：

| 检查维度 | 检查方向 |
|---------|---------|
| 入口可发现性 | 功能入口是否醒目可发现、引导是否充分、首次进入的新手指引 |
| 流程连贯性 | 从入口到核心体验到退出，全流程是否连贯无断裂、无多余等待或跳转 |
| 首次体验 | 首次进入时目标是否明确、学习成本是否合理、是否有渐进式引导 |
| 重复体验 | 重复进入时是否有效率通道（跳过已知内容）、是否有持续新鲜感 |
| 退出体验 | 退出/结束时是否有清晰的结束感、是否有续玩钩子 |
| 情绪节奏 | 体验过程中的高低起伏是否合理、是否有持续无聊或持续高压的段落 |

#### 2.2 动效与视觉表现

| 检查维度 | 检查方向 |
|---------|---------|
| 界面转场 | 界面打开/关闭/切换是否有过渡动效、转场是否流畅无闪烁 |
| 元素出现/消失 | UI元素、玩法元素的出现和消失是否有合理动效（淡入淡出/缩放/滑入） |
| 数值变化 | 数值增减是否有动画表现（滚动数字/飘字/进度条动画） |
| 状态切换 | 按钮/卡片/模块的状态变化是否有视觉过渡（高亮/变色/缩放） |
| 技能/打击动效 | 攻击命中、技能释放、打击反馈的特效是否到位（顿帧/震屏/粒子） |
| 场景动效 | 场景内的动态元素（天气/光照/环境物）是否有自然的动态表现 |

#### 2.3 音乐与音效

| 检查维度 | 检查方向 |
|---------|---------|
| BGM 切换 | 场景/阶段/状态切换时 BGM 是否及时切换、过渡是否自然（淡入淡出） |
| 操作音效 | 按钮点击、确认/取消、获得/消耗等操作是否有对应音效反馈 |
| 环境音 | 场景环境音是否匹配氛围、是否有空间感（3D音效定位） |
| 战斗音效 | 攻击/受击/技能释放/命中反馈的音效是否到位、是否有打击感 |
| 成就/奖励音效 | 获得奖励/完成目标/达成成就时是否有正向反馈音效 |
| 音量层次 | 多个音效同时播放时是否有合理的音量层次、是否互相遮盖 |

#### 2.4 UE 反馈与交互感知

| 检查维度 | 检查方向 |
|---------|---------|
| 操作确认感 | 每次操作是否有明确的反馈（视觉+听觉+触觉/震动三重确认） |
| 状态感知 | 当前状态（进行中/已完成/不可用）是否可通过视觉一目了然 |
| 等待反馈 | 网络请求/加载过程是否有进度指示、长等待是否有焦虑缓解设计 |
| 错误反馈 | 操作失败/条件不足时是否有清晰的原因说明和引导 |
| 容错设计 | 危险操作（消耗/删除/不可逆）是否有二次确认、误操作是否可撤回 |
| 信息层次 | 界面信息是否有清晰的主次层次、核心信息是否第一眼可见 |
| 红点/提示 | 红点提示是否及时出现和消除、是否准确引导用户关注点 |

#### 2.5 领域体验专项

根据 Step 1 识别的领域标签，从对应领域 Skill 中读取「体验检查方向」节，生成领域特有的体验检查：

- `#system` → 读取 `req-system` 的「体验检查方向（系统策划）」
- `#gameplay` → 读取 `req-gameplay` 的「体验检查方向（玩法策划）」
- `#leveldesign` → 读取 `req-leveldesign` 的「体验检查方向（关卡策划）」

**领域专项不重复通用维度**：如果某个领域体验维度已被 2.1-2.4 的通用维度覆盖，则不在此重复，仅补充领域独有的检查点。

**生成规则**：
1. 只选择与文档内容**实际相关**的体验维度，不机械罗列全部维度
2. 结合文档具体内容，将体验维度转化为可操作的验证描述
3. 跨领域文档合并各领域的体验检查方向
4. 当某个体验维度包含多个独立检查点时，使用二级嵌套

### Step 3：生成功能完整性检查（精简）

功能完整性检查作为兜底，采用"核心流程验证"模式，只聚焦主干：

1. **核心流程验证**：每个功能模块的主干流程是否可端到端走通（入口→操作→结果）
   - 每个功能模块生成一条主检查项，仅覆盖关键路径
2. **关键异常**：仅保留文档中**明确描述**的关键异常处理（不罗列通用异常场景）
3. **数据联通**：配置表参数是否生效 + 跨系统联动是否正常，合并为一条检查

**精简原则**：
- 功能完整性条目数量应显著少于体验检查条目
- 简单文档（1-2 个模块）保持一级结构，不使用嵌套
- 复杂文档（≥3 个模块）允许二级嵌套，但每个模块最多展开 2 个子项

### Step 4：输出清单

1. 按输出格式组织验收检查清单（体验在前、功能在后）
2. **standalone 模式**：以 Markdown 格式输出，提示用户将清单追加到需求文档末尾
3. **embedded 模式**：将清单作为文档最后一个章节，使用 `## 验收检查清单` 标题追加

---

## 注意事项

- **体验优先**：体验检查是清单的核心产出，应占清单总条目的 **60%-70%**；功能完整性检查占 **30%-40%**
- **不做格式审查**：本 Skill 不检查文档是否符合 `doc-format-standard` 的格式规范，不评判文档质量（standalone 模式）
- **不做内容重写**：不修改、不重写文档已有内容，仅基于已有内容生成清单
- **忠于文档内容**：功能完整性检查项必须来自文档实际描述的功能模块，不凭空推测未提及的功能
- **体验检查可适度外推**：体验检查部分可以基于功能特征推断合理的体验关注点，即使文档未明确提及动效/音效等
- **简洁优先**：清单条目应简洁明了，每条聚焦一个可验证的点；避免复述文档中的详细规则
- 当用户提供的文档内容不完整或过于简略时，提示用户补充后再生成，或基于已有内容生成并标注覆盖范围有限
