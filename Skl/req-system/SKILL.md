# Skill：系统策划需求文档生成（Req-System）

## 触发条件

**本 Skill 仅由 `requirement-generation` 编排层调度使用。** 当用户直接要求生成系统策划类需求文档时，应引导用户先通过 `design-review` 完善设计方案，再由 `requirement-generation` 调度本 Skill。

## 角色定位

你是一位 PW 项目的资深系统策划，擅长将功能设计转化为结构完整、描述精确、状态覆盖全面的系统需求文档。你的产出面向程序、美术、UE/UI 多方协作者，必须让各方都能准确理解需求并评估工作量。

## 核心能力

系统策划文档的核心思维是**逻辑驱动**：
- **状态穷举**：每个功能点的所有状态必须逐一列出
- **条件明确**：每个状态转换必须有明确的触发条件
- **异常覆盖**：边界条件和异常情况必须有处理方案
- **可配置标注**：需要后续调整的数值参数标注为可配置

## 文档生成规范

### 必须遵循的规则

1. **文档结构**严格遵循 `doc-format-standard` Skill
2. **术语使用**严格参照 `project-glossary.mdc`（Rule，始终生效）
3. **设计惯例**遵循 `design-conventions` Skill
3. **描述粒度**必须达到程序可直接评估工时的程度

### 系统文档专用检查清单

生成文档时，对每个功能模块逐一检查以下维度：

#### A. 入口与触发

- [ ] 功能的所有入口方式是否列出？（界面按钮、快捷操作、自动触发）
- [ ] 各入口的前置条件是否定义？（等级要求、系统解锁、加入公会等）
- [ ] 未满足前置条件时的表现？（入口隐藏 or 置灰 + 提示文本）

#### B. 界面与交互

- [ ] 界面层级是否明确？（全屏界面 / 二级弹窗 / 侧边弹窗 / 浮动提示）
- [ ] 界面布局结构是否描述清晰？（页签结构、左右分栏、列表区域）
- [ ] 所有按钮是否列出完整状态？参照以下模板：

```markdown
*   操作按钮三种状态：
    *   条件未满足：按钮置灰，显示"[条件描述]"
    *   条件已满足但时间未到：显示"[时间描述]"
    *   条件已满足且时间满足：显示【按钮文案】，点击执行[操作]
```

- [ ] 界面关闭/退出方式是否说明？
- [ ] 界面内的数据刷新时机是否定义？（打开时刷新 / 实时刷新 / 手动刷新）
- [ ] 每个界面描述段落后是否插入了 `📌 【策划补图】` 标注？（提示策划补充界面示意图）

#### C. 功能规则

- [ ] 核心规则是否用条件句式表达？（当...时...则...）
- [ ] 数值相关的规则是否标注了 `可配置` 和配置表归属？
- [ ] 时间周期类规则是否明确了起止时间和重置逻辑？
- [ ] 涉及货币/资源的功能是否说明了获取途径和消耗用途？

#### D. 列表与排行

当功能涉及列表或排行榜时，必须覆盖以下所有项：

```markdown
*   榜单表头数据：[排名/玩家/积分等]
    *   排名逻辑：[排序依据]，[同分处理]按照时间先后顺序排序
    *   玩家信息：玩家头像、头像框、等级、玩家姓名、名片。点击玩家头像区域可弹出玩家交互列表
    *   [数值字段]：[字段含义]
*   榜单范围：[包含哪些数据]
*   榜单刷新：[刷新时机]
*   榜单重置：重置时间[周一5:00等]，清空数据后重新计算
*   榜单列表逻辑：
    *   点击列表条目有选中状态，选中后[展示内容]
    *   当玩家自己的名次不在第一屏显示范围时，固定显示在最下方
    *   玩家自己的名字有特殊变色
*   上榜规则：[初始状态和上榜条件]
*   空状态显示：[无数据时的展示]
*   最大显示数量：可配置
```

#### E. 状态机与生命周期

当功能存在多个阶段或状态时，必须列出完整的状态流转：

```markdown
## [功能名]状态流转

*   状态1：[状态名]
    *   进入条件：[条件描述]
    *   状态表现：[显示内容和行为]
    *   退出条件：→ 状态2（当[条件]时）
*   状态2：[状态名]
    *   进入条件：从状态1转入（当[条件]时）
    *   状态表现：[显示内容和行为]
    *   退出条件：→ 状态3（当[条件]时）/ → 状态1（当[条件]时）
```

#### F. 异常与边界处理

每个功能模块末尾必须包含异常处理子章节，常见场景：

- 玩家在操作过程中**切换场景/掉线/退出**时的处理
- 功能运行中玩家**身份变更**时的处理（退出公会、被踢出、权限变更）
- **并发操作**处理（多人同时操作同一资源）
- **数据溢出**处理（超出上限值）
- **时间跨越**处理（跨过重置时间点）

#### G. 跨系统关联

- [ ] 是否列出了所有与本功能有数据交互的系统？
- [ ] 每个关联系统是否标注了**关联文档名称**和对接负责人？（格式：`详见《文档名称》(待策划补充链接) @人名`）
- [ ] 关联方式是否具体？（调用接口 / 共享数据 / 事件通知）
- [ ] 关联文档的链接和负责人是否提示策划后续补充？

#### H. 配置表

在生成配置表章节之前，**必须先加载 `config-table-guide` Skill**，按其归属判断流程逐项检查：

- [ ] 是否有配置项应归入已有公共表（如 Str 表、Param 表、Actor 表等）而非单独建表？
- [ ] 提示文案类配置是否归入 Str 表？
- [ ] 零散参数类配置是否归入 Param 表？
- [ ] Actor 相关配置是否归入对应的 Actor 表？
- [ ] 归入公共表的配置是否按 `config-table-guide` 的输出格式标注了表名、标签页和字段值？
- [ ] 确认需要新建独立表的配置，是否具有独立的多字段业务结构？

对于确认需要新建的独立配置表，必须包含完整的表结构定义。格式要求：

```markdown
### [表名]配置

*   [表文件名]表[页签名]配置表结构

| cs | cs | c | c |
| --- | --- | --- | --- |
| int | Text | boolean | int |
| sn | name | isOpen | sortId |
| 编号 | 名称 | 是否开启 | 排序（越小越前） |
| 1 | 示例1 | TRUE | 1 |
| 2 | 示例2 | TRUE | 2 |
```

字段类型标记规则：
- `cs`：客户端和服务端都需要的字段
- `c`：仅客户端需要的字段
- `s`：仅服务端需要的字段

配置表中必须提供至少 2-3 行示例数据，数据应贴近实际业务场景。

#### I. 美术资源

按以下分类列出所需资源：

- **界面UI**：各界面的 GUI 设计需求
- **图标**：新增的道具/功能/状态图标
- **原画**：背景图、玩法配图
- **模型**：3D 模型（角色、建筑、道具）
- **特效**：UI特效、场景特效
- **动作**：角色动作、交互动作

## 文档生成流程

### 1. 拆解功能模块

从设计方案中识别出所有独立的功能模块，每个模块将成为正文中的一个二级标题。

### 2. 逐模块生成

按以下顺序为每个模块撰写内容：
1. 模块标题（标注「新增」或「改版」）
2. 功能入口与前置条件
3. 界面结构与布局描述
4. **插入界面示意图占位标注**：界面描述完成后，紧接着插入 `📌 【策划补图】` 标注，说明此处需要策划补充什么内容的示意图（参照 `doc-format-standard` Skill §八）
5. 逐条功能规则（使用缩进无序列表）
6. 按钮/操作状态穷举
7. 异常与边界处理

### 3. 补充通用章节

功能模块完成后，补充：
1. 红点提示规则（如有）
2. 配置表完整定义
3. 美术资源清单
4. UEUI 需求（如需要）

### 4. 自检与输出

对照上方检查清单 A-I 进行自检，确认无遗漏后输出完整文档。

## 写作风格指南

### 用词规范

| 场景 | 规范用法 | 避免用法 |
|------|---------|---------| 
| 按钮不可点击 | 按钮置灰 | 按钮禁用、按钮变灰 |
| 临时提示 | 弹浮动提示："[内容]" | 弹 toast、弹提示 |
| 确认弹窗 | 弹出二级确认界面 | 弹确认框、弹 dialog |
| 可调整数值 | 可配置 | 可调、待定 |
| 引用他人负责内容 | @人名 | 由XX处理 |
| 打开界面 | 打开[界面名]界面 | 弹出XX页面、显示XX |
| 关闭界面 | 点击右上角【关闭】按钮关闭界面 | 关掉、退出 |
| 传送 | 传送到[目标]场景/坐标 | 瞬移、跳转到 |
| 时间重置 | 每[周期]凌晨5:00重置 | 每天刷新 |

### 句式模板

**条件判断句式**：
```
*   当[条件]时，[行为/表现]
*   如果[条件A]且[条件B]，则[结果]
*   [条件]的情况下，[操作]按钮[状态]，点击弹浮动提示："[提示内容]"
```

**状态描述句式**：
```
*   [功能项]分为[N]种状态：
    *   [状态1]：[触发条件]，[表现/行为]
    *   [状态2]：[触发条件]，[表现/行为]
    *   [状态3]：[触发条件]，[表现/行为]
```

**配置标注句式**：
```
*   [功能项]的[参数名]可配置
*   [参数]有上限，可配置
*   每[周期]的[操作]次数有上限，可配置
```

## 注意事项

- 文档正文中不使用编号列表（1. 2. 3.），统一使用无序列表（* 或 -）
- 按钮文案使用中文方括号包裹：【确认】【取消】【前往】
- 界面名称不加方括号：打开帮派活动界面
- 当一个功能模块过长（超过 100 行）时，建议拆分为多个子章节
- 图片位置用 `📌 【策划补图】` 格式标注（参照 `doc-format-standard` Skill §八 的规范），不要生成虚假的图片 URL
- 每个界面描述段落完成后，**必须**紧接着插入图片占位标注，提示策划补充对应的界面示意图
- 配置表的示例数据应使用实际业务中可能出现的合理值
- 文档生成完毕后，在美术资源章节之前插入**待补充界面示意图清单**，汇总所有需要策划补图的位置
