# Skill：PW 设计惯例与约束（Design Conventions）

## 触发条件

本 Skill 由 `design-review` Skill 和 `requirement-generation` 编排层在工作时加载使用。AI 在进行设计评审（Phase 1）和需求文档生成（Phase 2）时，**必须将以下惯例作为检查基线**。

---

## 一、核心设计原则

### 1.1 单人体验优先，多人兼容必查

所有以单人体验为目标的玩法/功能，在设计时**必须同时考虑多人场景下的意外情况**：

- **可见性**：其他玩家能否看到当前玩家的玩法状态和元素？看到的表现是什么？
- **冲突处理**：多个玩家同时触发同一玩法时如何处理？（先到先得 / 各自独立 / 排队等待）
- **干扰隔离**：其他玩家的行为（攻击、推挤、抢夺交互）是否会干扰当前玩家？
- **联机/同居模式**：组队、同居等社交模式下是否存在特殊兼容问题？

> **检查句式**：「如果两个玩家同时做这件事，会发生什么？」——每个玩法设计必须能回答这个问题。

### 1.2 不重复造轮子，优先复用已有框架

设计新功能时，**必须先检查项目中是否已有可复用的框架或流程**：

- 已有框架能满足需求时，不新建系统（如：变身球投掷复用"捕捉尸体"流程，而非新建"帕鲁精华"系统）
- 引用已有框架时，使用「走[框架名]流程」的表述，不重复描述框架内部逻辑
- 限时类玩法优先接入「限时挑战框架」
- 变身类玩法优先接入「帕鲁变身解谜框架」

> **检查句式**：「这个功能是否能用现有的某个框架/流程实现？如果能，为什么不用？」

### 1.3 操作限制必须配对恢复

进入特殊状态（变身、挑战、副本等）时限制的所有操作，**必须在退出状态后逐一恢复**，且需要：

- 限制项使用无序列表逐条列出
- 列表末尾包含恢复声明：「以上无法执行的操作在[状态名]结束后恢复」
- 隐藏的 UI 按钮必须在恢复时重新显示

### 1.4 可配置优先，禁止硬编码

所有需要调整的数值参数（时间、距离、数量、等级等）**必须标注"可配置"并指明配置表位置**，不可在文档中写死确定值作为最终方案。允许提供默认值作为参考。

## 二、多人设计约束

### 2.1 多人可见性定义

任何涉及玩家外观/状态变化的功能，必须定义其他玩家的视角：

| 需定义项 | 说明 |
|---------|------|
| 模型表现 | 其他玩家看到变化后的玩家是什么样子？ |
| 名称显示 | 变化状态下玩家名字如何显示？ |
| 玩法元素 | 其他玩家能否看到当前玩家的玩法元素（NPC、道具、特效）？ |
| 进度独立性 | 玩法进度是个人的还是共享的？ |

### 2.2 多人冲突处理

框架级功能（如帕鲁神像、挑战触发点）需要明确：

- 多人同时交互时的优先级规则
- 玩法中的物理碰撞/推挤是否影响其他玩家
- 框架层提供通用规则还是由子玩法自行处理（需声明责任归属）

---

## 三、框架与子玩法的设计约束

### 3.1 框架文档必须定义子文档接口

当一个功能作为框架（供多个子玩法接入）时，框架文档**必须包含以下接口定义**：

- **可用模式**：框架支持哪些工作模式（如"指定帕鲁/任意帕鲁"），子玩法如何选用
- **可配置参数**：框架暴露给子玩法的配置项列表
- **配置表结构**：子玩法需要引用的框架配置表及其字段
- **状态回调**：框架在哪些时机通知子玩法（如"变身完成"、"超时退出"）
- **子玩法责任边界**：哪些逻辑由框架处理，哪些由子玩法自行实现

### 3.2 子玩法文档的引用规范

子玩法引用框架时：

- 标注「走[框架名]流程」，不重复描述框架内部逻辑
- 说明使用的框架模式（如"帕鲁神像配置为'指定帕鲁'模式"）
- 仅描述子玩法独有的逻辑和框架预留的扩展点

---

## 四、跨系统设计规则

### 4.1 系统影响标注

当功能涉及其他系统时：

- 在「功能对其他游戏系统的影响」中逐条列出
- 每条使用**跨系统引用格式**标注关联文档和负责人：`详见《[关联文档名称]》([文档链接/编号]) @负责人`
- 当文档链接暂不可用时，使用 `(待策划补充链接)` 占位，**不可省略文档名称**
- 说明影响方式（数据读取 / 数据写入 / UI联动 / 逻辑依赖）

### 4.2 常见联动系统清单

以下系统在设计时需特别关注是否存在联动：

| 系统 | 典型联动场景 |
|------|------------|
| 帕鲁球系统 | 投掷逻辑复用、槽位替换、HUD变化 |
| 背包系统 | 道具获得/消耗、容量检查、物品展示 |
| 货币系统 | 购买/出售结算、货币类型、余额不足处理 |
| 邮件系统 | 奖励发放、背包满时转邮件 |
| 帕鲁AI/仇恨系统 | 阵营关系、仇恨触发/解除规则 |
| 场景系统 | 蓝图种植、birthSn关联、导演配置 |
| 限时挑战框架 | 框架接入、计时/计数HUD、成败结算 |

### 4.3 仇恨/阵营关系变化

涉及玩家与帕鲁/NPC关系变化的功能，必须在框架层明确定义：

- 基础仇恨规则（同种友好/异种中立/敌对维持等）
- 主动攻击时的仇恨触发逻辑
- 规则的配置方式（阵营配置 / 白名单 / 硬编码）

## 五、状态管理约束

### 5.1 异常场景必须覆盖

所有涉及特殊状态（变身、挑战中、副本内等）的功能，必须定义以下异常场景的处理：

| 异常场景 | 必须定义的处理 |
|---------|-------------|
| **断线重连** | 重连后的状态（回到变化前 / 保持状态 / 强制退出） |
| **场景切换/传送** | 状态是否保留、道具是否消失 |
| **玩家死亡** | 特殊状态如何结束、恢复后的玩家状态（HP等） |
| **超时** | 预警表现（最后N秒闪烁/音效）、超时后的处理 |
| **卡地形/卡模型** | 是否提供紧急退出机制 |

### 5.2 首次体验引导

新功能/新玩法在玩家首次触发时，应设计引导机制：

- 首次交互时弹出玩法引导说明
- 引导信息不阻塞核心操作流程
- 引导仅首次触发，后续不再重复

---

## 六、已知技术约束

以下是项目中已知的技术限制，设计阶段需提前考虑：

| 约束 | 说明 | 设计建议 |
|------|------|---------|
| 变身3C调试 | 每个帕鲁的变身操控手感需单独调试 | 首批支持帕鲁数量控制在5-8种内 |
| 碰撞体积变化 | 体型变化后可能导致卡地形 | 提供紧急退出机制 |
| 同屏特效性能 | 大量特效同屏影响帧率 | 限制单场景内同时活跃的特效数量 |
| 多人同步开销 | 变身/状态变化需网络同步 | 减少高频同步的状态字段 |
| 蓝图参数限制 | 蓝图参数类型受引擎支持范围限制 | 复杂配置优先走配置表 |

## 七、文件输出约定

### 7.1 默认工作区路径

所有 Skill 产出的本地文件（需求文档、美术需求 Excel 等）**默认保存到以下目录**：

```
~/user/lbworkspace/
```

- 该路径在不同系统上自动展开为用户主目录下的 `user/lbworkspace/`
- 如果目录不存在，由保存操作自动创建
- 用户明确指定了其他路径时，以用户指定的路径为准

### 7.2 保存后必须提示

每次将文件保存到本地后，**必须**在对话中明确告知用户：

1. 文件的完整保存路径
2. 保存了哪些文件（如同时保存了 markdown 和 Excel，逐一列出）

示例提示格式：
```
📁 文件已保存：
  - 需求文档：~/user/lbworkspace/需求文档_交易行系统.md
  - 美术需求：~/user/lbworkspace/美术需求_交易行系统.xlsx
```
