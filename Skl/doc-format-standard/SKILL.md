# Skill：PW 需求文档格式规范（Doc Format Standard）

## 触发条件

本 Skill 由 `requirement-generation` 编排层或各领域 Skill（`req-system`、`req-gameplay`、`req-leveldesign` 等）在生成文档时加载使用。

## 角色定位

本 Skill 提供 PW 项目需求文档的**格式底线规范**。所有 AI 生成的需求文档必须严格遵循此规范中定义的结构、章节和字段要求。

---

## 一、文档元信息（必填）

文档顶部必须包含以下两个表格：

### 1.1 基本信息表

| 字段 | 要求 | 说明 |
|------|------|------|
| **项目名称** | 必填 | 填写 `PW` 或 `PW-UE`（需要UE参与时） |
| **保密级别** | 必填 | 默认填 `秘密` |
| **UE评级** | 视情况 | 需要UE介入时填写 `需要UE`，否则可省略 |
| **作者名称** | 必填 | 策划人员姓名 |
| **一审人** | 必填 | 主审人姓名 |
| **二审人** | 选填 | 副审人姓名 |
| **文档版本** | 必填 | 使用 x.x 格式，如 `1.0`、`1.1` |
| **日期时间** | 必填 | 格式：`YYYY年MM月DD日` |

格式示例：

```markdown
| **项目名称** | **PW-UE** |
| --- | --- |
| **保密级别** | **秘密** |
| **UE评级** | **需要UE** |
| **作者名称** | _**作者姓名**_ |
| **一审人** | _**审核人姓名**_ |
| **二审人** | _**审核人姓名**_ |
| **文档版本** | 1.0 |
| **日期时间** | **YYYY年MM月DD日** |
```

### 1.2 修改记录表

| 字段 | 要求 |
|------|------|
| **修改人名** | 必填 |
| **版本号** | 必填，与基本信息表的版本对应 |
| **时间** | 必填，格式 `YYYY/MM/DD` 或 `YYYY.MM.DD` |
| **修改内容** | 必填，简要说明本次修改的内容 |

---

## 二、前言章节（必填）

前言为一级标题 `# 前言`，包含以下子章节：

### 2.1 设计目的（必填）

- 用无序列表说明本功能的**方向性设计目标**，聚焦于"为什么做"
- 应写**宏观层面的目的和方向**，以及与其他系统的战略关系，不涉及具体实现细节
- 抽象层级：一句话能概括整个功能的存在意义

> **正例**：「提供一个低社交成本且日常产出奖励的异步社交方式，籍此引导玩家接触并将玩家导入更深度的社交功能」
>
> **反例**：「通过每日拜访获得金币和经验，拜访时展示好友家园的建筑」（❌ 这是实现细节，不是设计目的）

- **重要**：设计目的应优先由策划本人表述，AI 负责润色和结构化。当策划未提供设计目的时，AI 应主动询问：「请用 1-2 句话描述这个功能为什么要做、希望达到什么效果？」

### 2.2 如何达到设计目的（必填）

- 用无序列表说明实现路径
- 每条应是对**整个文档内容的高度概括性总结**，描述设计策略和方法论，而非具体的实现步骤
- 抽象层级：读者看完这一节，应能在不阅读正文的情况下理解功能的整体思路

> **正例**：「通过异步拜访机制降低社交门槛，让不在线的好友也能产生互动收益」
>
> **反例**：「玩家点击好友列表中的拜访按钮，进入好友家园场景，点击家具获得金币奖励」（❌ 这是操作流程描述，不是方法论概括）

### 2.3 功能对其他游戏系统的影响（必填）

- 列出本功能会影响的其他系统
- 如无影响，写 `暂无`
- 每条关联必须使用**跨系统引用格式**（见 §七 第5条），包含关联文档名称和负责人

### 2.4 名词解释（条件必填）

- 当文档中引入了非通用术语或本文特有的概念时必须提供
- 格式：`术语名：解释内容`

### 2.5 风险评估（选填）

- 列出已知风险点
- 如无风险，写 `暂无`

---

## 三、正文章节（必填）

正文为一级标题 `# 正文`，包含以下子章节：

### 3.1 功能概述（必填）

- 用无序列表概括本文档涵盖的所有功能模块
- 作为正文内容的索引和概览

### 3.2 功能规则（必填，按模块展开）

每个功能模块为二级或三级标题，须包含：

- **规则描述**：使用无序列表逐条描述功能规则
- **状态/条件分支**：不同条件下的不同表现必须逐一列出
- **UI 说明**：涉及界面时描述显示内容、布局、交互行为
- **异常处理**：边界情况和异常状态的处理方式
- **关联说明**：与其他系统/模块的交互点，使用 `@人名` 标注对接人

#### 规则描述的格式要求

1. **层级结构**：使用缩进的无序列表表达从属关系
2. **状态穷举**：涉及多状态的功能，必须列出所有状态及其对应行为
3. **条件判断**：使用 `当...时` / `如果...则` 的句式明确触发条件
4. **数值引用**：需要配置的数值用 `可配置` 标注，不要硬编码
5. **图片引用**：界面示意图使用 `![描述](url)` 格式内嵌。**当正文涉及界面布局描述时，必须在描述段落后插入图片占位标注**（见 §八 界面示意图插入规范）

#### 规则描述示例

```markdown
## 帮派捐献（新增）

*   界面标题"捐献"
*   捐献类型：现金捐献、金币捐献，可配置
*   获得奖励：帮派币、帮派活跃度，可配置
*   每日捐献次数有上限，可配置
    *   今日剩余捐献次数>0时，点击【捐献】按钮执行操作：扣除花费、获得对应奖励
    *   今日剩余捐献次数为0时，【捐献】按钮置灰，点击弹浮动提示：今日捐献次数已用完
    *   当前捐献花费不足时，【捐献】按钮不置灰，点击弹浮动提示：捐献余额不足
*   捐献次数每日凌晨5:00重置
```

### 3.3 按钮/操作状态的描述规范

涉及 UI 按钮或交互操作时，必须完整列出所有状态：

- **正常状态**：默认显示和行为
- **置灰/不可点击状态**：触发条件和点击后的提示
- **高亮/可领奖状态**：触发条件和视觉效果
- **已完成/已领取状态**：视觉效果和交互限制

### 3.4 列表/排行榜的描述规范

涉及列表或排行显示时，须说明：

- **表头字段**：每列的含义
- **排序规则**：排序依据、同分处理逻辑
- **数据范围**：包含哪些数据
- **刷新机制**：何时刷新数据
- **重置机制**：何时清空数据
- **自身定位**：当前玩家在列表中的特殊显示规则
- **空状态**：无数据时的展示方式

---

## 四、配置规则章节（必填）

为一级或二级标题 `# 配置规则` 或 `## 配置规则`。

### 4.1 配置表定义

每张配置表须包含：

- **表名和页签名**（如：Union表 UnionTask页签）
- **表结构**：使用表格展示，包含以下行：
  - 第一行：字段类型标记（`cs` 客户端+服务端 / `c` 仅客户端 / `s` 仅服务端）
  - 第二行：数据类型（`int` / `Text` / `boolean` / `int[]` / `String`）
  - 第三行：字段英文名
  - 第四行：字段中文说明
  - 后续行：示例数据

#### 配置表格式示例

```markdown
| cs | cs | c |
| --- | --- | --- |
| int | int | Text |
| sn | cost | reward |
| sn（捐献次数） | 消耗 | 获得奖励 |
| 1 | 6:100 | 11:30 |
| 2 | 7:100 | 11:30 |
```

### 4.2 枚举/类型定义表

当功能涉及类型枚举时，须提供独立的类型说明表。

### 4.3 参数配置

使用 param 表的配置项须列出字段名和默认值。

---

## 五、美术资源章节（必填）

为一级标题 `# 美术资源`。

- 使用无序列表逐项列出所需的美术资源
- 每项说明资源类型和用途
- 常见分类：界面UI、图标、原画、模型、特效、动作

---

## 六、UEUI需求章节（条件必填）

当文档元信息中 UE评级 为 `需要UE` 时，须包含此章节：

- 列出需要 UE 参与设计的界面和交互
- 简要描述 UE 关注点

---

## 七、全局格式约束

1. **标题层级**：一级标题用于大章节（前言、正文、配置规则、美术资源），二级及以下用于功能模块
2. **列表格式**：统一使用 `*` 或 `-` 的无序列表，同一文档内保持一致
3. **强调格式**：重要规则或关键词使用 `**加粗**`
4. **可配置标注**：所有需要策划配置的数值参数，在描述中标注 `可配置` 或指明配置表位置
5. **跨系统引用**：引用其他系统功能时，必须使用以下格式标注关联文档和负责人：
   - **格式**：`详见《[关联文档名称]》([文档链接/编号]) @负责人`
   - **示例**：`详见《帕鲁捕捉系统需求文档》(待策划补充链接) @张三`
   - 当文档链接暂不可用时，使用 `(待策划补充链接)` 占位，**不可省略文档名称**
   - AI 生成文档时应主动标注关联文档名称，链接和负责人由策划后续补充
6. **新增/改版标注**：功能标题后标注 `（新增）` 或 `（改版）` 表明变更类型
7. **图片引用**：界面线框图或示意图使用 Markdown 图片语法内嵌
8. **红点/提示规则**：涉及红点提示时，须说明红点传递链路（如：功能入口←父入口←菜单入口）

---

## 八、界面示意图插入规范

AI 生成的文档中**不可能包含真实的界面截图**，因此必须通过占位标注提示策划后续补充。

### 8.1 必须插入图片标注的场景

以下场景在描述完成后，**必须紧接着插入图片占位标注**：

| 场景 | 说明 |
|------|------|
| **界面整体布局描述** | 描述一个界面的分区、页签结构、左右分栏等布局时 |
| **复杂交互流程** | 涉及多步操作、状态切换的交互流程时 |
| **界面元素排列** | 描述列表、卡片、图标等元素的排列方式时 |
| **特殊视觉效果** | 描述动画、特效、高亮等视觉表现时 |

### 8.2 图片标注格式

```markdown
> 📌 **【策划补图】**：此处需要插入 **[图片内容描述]** 的界面示意图，应展示：[图片应包含的关键要素]
```

**示例**：
```markdown
> 📌 **【策划补图】**：此处需要插入 **帮派捐献界面整体布局** 的界面示意图，应展示：捐献类型选择区域、奖励预览区域、捐献按钮位置、剩余次数显示位置
```

### 8.3 文档末尾汇总

文档生成完毕后，在美术资源章节之前，插入一个**待补充示意图汇总**：

```markdown
## 待补充界面示意图清单

以下位置需要策划补充界面示意图或线框图：

1. [§正文 > 模块A] — [图片内容描述]
2. [§正文 > 模块B] — [图片内容描述]
3. ...

请策划完成示意图后替换对应位置的占位标注。
```
